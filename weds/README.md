# Wedns

Проверка локальных LLM на готовность к агентской работе.

Инструмент отвечает на один вопрос: **можно ли на этой модели работать агентом, а не только
болтать в чате.** Проверяет, влезает ли системный промпт агента в контекст, умеет ли модель
вызывать инструменты, не ломается ли JSON в аргументах, кэшируется ли префикс и с какой
скоростью всё это едет на конкретном железе.

Без зависимостей - только стандартная библиотека Python 3.9+.

> Команды ниже запускаются **из корня репозитория** (`python weds.py …`), а не из этой
> папки: `weds.py` лежит в корне, здесь только модули. Второе приложение репозитория -
> пульт для локальных моделей, о нём в корневом [`README.md`](../README.md).

---

## Зачем это появилось

Реальный случай, который и стал причиной написать инструмент.

Модель подняли в LM Studio, прописали в конфиг агента, выбрали в UI. В ответ:

```
Custom model custom-local:ornith-1.5-9b-crack error. Please switch model or retry.
```

Ни причины, ни числа, ни подсказки. Полезли в лог движка:

```
Engine protocol predict request returned 400:
request (37955 tokens) exceeds the available context size (32768 tokens)
```

Оказалось, **системный промпт агента с описаниями инструментов - 37 955 токенов**.
Контекст стоял 32768. Модель была совершенно ни при чём.

Дальше выяснилось, что это не единственная мина:

- Контекст подняли до 49152 - и генерация обвалилась с 41 до **2.3 tok/s**. Потому что
  KV-кеш в q8_0 перестал влезать в 8 ГБ VRAM. При этом **префилл остался быстрым** (~880 tok/s),
  что сбивает с толку: кажется, что железо ни при чём.
- Часть слоёв по умолчанию осталась на CPU (`offloadRatio 0.8125`), и полный оффлоад дал
  **2.3× прироста** - 17.8 → 41 tok/s.
- `flashAttention` по умолчанию **выключен**.
- LM Studio **не блокирует переполнение VRAM**: он спокойно грузит конфиг, которому нужно
  12.9 ГБ, на карту с 8 ГБ. Драйвер уходит в пейджинг по PCIe, и тормозит **вся система**,
  а не только модель.
- Повторные загрузки с разными параметрами создают **второй инстанс** модели
  (`model:2`), и два 9B живут в памяти одновременно.

Ни одну из этих проблем не видно из UI. Wednesday находит их за один прогон.

## Первый запуск: по шагам

Инструкция для того, кому папку просто передали. Установки нет: распаковал, запустил.

### Что должно быть на машине

| Что | Зачем | Обязательно |
|---|---|---|
| Python 3.9+ | запустить сам `weds` | **да** |
| Локальный сервер с OpenAI-совместимым HTTP API | LM Studio / Bionic, Ollama, llama.cpp | **да** |
| Скачанная модель в этом сервере | то, что проверяем | **да** |
| `lms` CLI | `tune`, `load`, `logs` | только для LM Studio |

Внешних библиотек не нужно, `pip install` не требуется - только стандартная библиотека.
Ничего не пишется за пределы папки, кроме явного `register` и `tune --apply` (оба делают бэкап).

### Шаг 1. Проверить Python

```bash
python --version        # Windows
python3 --version       # Linux / macOS
```

Нужен 3.9 или новее. Если `python` не найден, на Windows обычно работает `py --version` -
тогда во всех командах ниже пиши `py` вместо `python`.

Дальше все команды - из корня распакованной папки:

```bash
cd <куда распаковал>\Wednesday
```

### Шаг 2. Убедиться, что инструмент живой

```bash
python weds.py --help
```

Печатается список команд - значит всё на месте, можно идти дальше.

### Шаг 3. Поднять сервер и загрузить модель

Делается **в самом сервере**, не в `weds`:

| Сервер | Как поднять | Порт |
|---|---|---|
| LM Studio / Bionic | вкладка Developer → Start Server | 1234 |
| Ollama | `ollama serve` | 11434 |
| llama.cpp | `llama-server -m model.gguf -c 32768` | 8080 |

Модель лучше **загрузить заранее**, а не оставлять «поднимется при первом запросе»:
LM Studio тогда грузит её минуты две, и `weds` может не дождаться по таймауту.
В LM Studio: `lms load <ключ модели>`, либо просто открыть чат с ней.

### Шаг 4. Проверить, что сервер виден

```bash
python weds.py discover
```

Ожидаемый результат - адрес и тип сервера. Если пусто, причины две:

1. Сервер не запущен.
2. Сервер на нестандартном порту или на другой машине в сети. Тогда адрес задаётся явно:

```bash
python weds.py discover --server-url http://127.0.0.1:8080
```

`--server-url` понимают все команды, которые ходят на сервер: `discover`, `models`, `check`,
`bench`, `doctor`, `register`. Через сеть тоже работает. Команды `tune`, `logs`, `load`,
`restore` работают с файлами LM Studio на этой машине и адрес не принимают.

### Шаг 5. Узнать id модели

```bash
python weds.py models
```

Скопируй значение из колонки **ID** - оно идёт в `--model`. Точное совпадение не требуется:
`--model ornith` подойдёт, если такая модель на сервере одна.

### Шаг 6. Диагностика одной командой

```bash
python weds.py doctor
```

Выводит: что запущено, что нашлось в логах движка, и полный набор проверок.
Коды возврата - удобно для скриптов и для агента:

| Код | Значение |
|---|---|
| `0` | PASS или WARN - работать можно |
| `1` | есть FAIL - модель к агентской работе не готова |
| `2` | сервер не найден |

### Шаг 7. Починить, если `context_fit` упал

Это самая частая проблема: системный промпт агента не влезает в контекст модели.

```bash
python weds.py tune --model <id>              # посмотреть, что предлагается
python weds.py tune --model <id> --apply      # записать в конфиг (с бэкапом)
```

Затем **перезагрузить модель** - параметры читаются только при загрузке:

```bash
python weds.py load --unload          # выгрузить всё (важно: иначе появится вторая копия модели)
python weds.py load --model <id>      # загрузить с новыми параметрами
```

И перепроверить:

```bash
python weds.py check --model <id>
```

Откатить, если стало хуже: `python weds.py restore --model <id>`.

### Шаг 8. Прописать модель в агента

```bash
python weds.py register --model <id> --target workbuddy
```

Доступные цели: `workbuddy`, `codebuddy`, `generic`, `env`. `--dry-run` покажет, что будет
записано, не трогая файл. В `maxInputTokens` подставляется **реально загруженный контекст** -
именно это число должно совпадать с контекстом модели, иначе агент снова получит 400.

После этого перезапустить агент и выбрать модель в списке.

### Шаг 9. (необязательно) Подключить как MCP

Чтобы агент сам мог запускать проверки - см. «Подключение к агентам» ниже.

## Разное железо, разные веса, другая ОС

Инструмент не привязан ни к одной конфигурации. Что меняется и как это учтено:

| Что различается | Как учитывается |
|---|---|
| **Видеокарта** | VRAM определяется сама: сначала `nvidia-smi`, а если NVML заблокирован - из реестра Windows (`HardwareInformation.qwMemorySize`, 64-битное поле). Работает и на AMD/Intel. |
| **VRAM не определилась** | `--vram-gib 12` - сказать вручную, сколько всего на карте |
| **Проекция говорит «не влезает», а на деле работает** | `--budget-gib 7` - задать бюджет памяти под модель напрямую, минуя расчёт «доля VRAM минус резерв». Оценщик LM Studio систематически завышает расход, так что это частый случай |
| **Нужно экономить видеопамять** | `--kv-in-ram` - держать KV-кеш в системной RAM. Медленнее примерно на треть, зато VRAM растёт слабо. По умолчанию кеш в VRAM |
| **Другая модель, другая квантизация** | Всё считается по конкретной модели: `--model <id>`. Кривая памяти снимается заново для каждой - никаких хардкодов под 9B |
| **Модель не влезает в VRAM целиком** | `tune` скажет об этом прямо и предложит `q4_0` для KV-кеша; часть слоёв уедет на CPU, скорость упадёт - это ожидаемо |
| **Слабая или сильная карта** | Пороги скорости относительные: `check` сравнивает с `--min-gen-tps` (по умолчанию 12 tok/s) |
| **Число ядер CPU** | Определяется **физическое** число, а не логическое: hyper-threading на инференсе только мешает |
| **Другая ОС** | `python3` вместо `python`. Обход VRAM через реестр - только Windows; на Linux/macOS работает NVML. Остальное кроссплатформенно |
| **Не-LM-Studio сервер** | `--kind ollama` / `llamacpp` / `generic`. `check`, `bench`, `register` работают полностью; `tune` - только LM Studio (у остальных нет per-model конфигов в таком виде) |
| **Другая агентская обвязка** | `--agent-tokens <N>` - размер системного промпта. По умолчанию 38000 (замерено на WorkBuddy) |

Порядок действий одинаковый на любой машине: `discover` → `models` → `doctor` → `tune --apply` →
`check` → `register`. Меняются только флаги из таблицы выше.

### Почему проверки отдельно от бенчмарков

`checks.py` отвечает «годится или нет» и всегда даёт **конкретный фикс**.
`bench.py` даёт голые числа без суждений. Смешивать не стоит: агент, который читает
`--json`, хочет видеть статус и рекомендацию, а человек, снимающий замеры, - цифры.

## Проверки

| Проверка | Что ловит |
|---|---|
| `server` | сервер не слушает порт |
| `model` | id модели не совпадает с тем, что отдаёт сервер |
| `context_exact` | какой контекст реально применился; модель не загружена (JIT-таймаут) |
| `context_fit` | **системный промпт агента не влезает в контекст** - главная мина |
| `tool_calling` | модель не возвращает `tool_calls` - агентская петля невозможна |
| `reasoning_overhead` | reasoning-модель жжёт сотни токенов на тривиальный вопрос |
| `prefix_cache` | кэш префикса не работает - каждый ход будет по 40 секунд |
| `prefill_speed` | холодный префилл слишком долгий |
| `gen_speed` | генерация обвалилась (чаще всего из-за переполнения VRAM) |

Размер промпта агента задаётся: `--agent-tokens 38000` (по умолчанию - замеренный на WorkBuddy).

Известные значения:

| Обвязка | Токенов |
|---|---|
| WorkBuddy | ~38 000 |
| Claude Code | ~24 000 |
| Cursor | ~20 000 |
| Codex | ~16 000 |

### Диагностический признак, который стоит запомнить

> **Префилл быстрый, генерация обвалилась в 15 раз → не хватает VRAM.**

Префилл обрабатывает память батчами и читает её последовательно, поэтому остаётся быстрым.
Генерация на каждый токен перечитывает KV-кеш вразнобой и упирается в PCIe. Это не баг модели
и не лечится перезагрузкой - только снижением KV-кванта или контекста.

## Подключение к агентам

### Как MCP-сервер (любой агент)

`weds.py mcp` поднимает MCP-сервер по stdio с восемью инструментами:
`local_llm_discover`, `local_llm_list_models`, `local_llm_check`, `local_llm_bench`,
`local_llm_tune`, `local_llm_register`, `local_llm_logs`, `local_llm_doctor`.

Конфигурация для Claude Code / Cursor / Codex / WorkBuddy:

```json
{
  "mcpServers": {
    "wednesday": {
      "command": "python",
      "args": ["F:\\Pets\\Cursor\\Wednesday\\weds.py", "mcp"]
    }
  }
}
```

Протокол: JSON-RPC 2.0 построчно, `initialize` → `tools/list` → `tools/call`.
Всё, что не протокол, идёт в stderr - stdout занят каналом протокола.

`skills/wednesday/SKILL.md` - чтобы агент сам знал, когда и как запускать проверку.
Скопировать в `~/.workbuddy-ai/skills/wednesday/`.

### Как обычный CLI

Любой агент с доступом к shell может звать `python weds.py check --json` и разбирать вывод.

## Как это работает внутри

### Кривая памяти

Ручной расчёт размера KV-кеша по метаданным GGUF **для гибридных архитектур врёт в разы**.
У Qwen3.5-Next (`qwen35`) полный attention только в каждой 4-й слое (`full_attention_interval=4`),
плюс есть SSM-ветка с константным состоянием. Прикидка «слои × головы × длина» даёт ошибку
и в большую, и в меньшую сторону.

Поэтому цена контекста **измеряется**, а не считается:

```bash
lms load <model> -c 8192  --estimate-only   # -> total(8192)
lms load <model> -c 32768 --estimate-only   # -> total(32768)

bytes_per_token = (total(8192) - total(32768)) / (32768 - 8192)
weights         = total(8192) - bytes_per_token * 8192
```

Модель при этом не загружается - система не нагружается. На реальной 9B получилось
**47.4 КиБ/токен** и вес **5.8 ГиБ**.

Важно: оценщик при этом **завышает** расход. Наблюдение с живой машины - проекция утверждала
«не влезает» при контексте 49152 на 8-гиговой карте, а модель на этом контексте выдавала
52 tok/s. Насколько именно завышает, зависит от архитектуры и версии движка, поэтому в `tune`
проекция используется как **предупреждение, а не как приговор**: окончательный ответ даёт
`weds bench` уже после загрузки. Если проекция мешает подобрать рабочий конфиг - бюджет
задаётся напрямую: `--budget-gib 7`.

### Квантование KV

Оценщик считает KV по своей базовой точности, близкой к `q8_0`. Реальный `q4_0` даёт
примерно половину, поэтому в `tune.py` есть коэффициент `KV_FACTOR`.

На 8 ГБ с моделью 5.8 ГиБ и промптом агента 38k токенов:

| KV | Цена | Итог на 49152 | Генерация |
|---|---|---|---|
| `q8_0` | ~47 КиБ/ток | 8.07 ГиБ | **2.3 tok/s** - вылет за 8 ГБ |
| `q4_0` | ~24 КиБ/ток | 6.74 ГиБ | **34 tok/s** |

Отсюда правило: `q8_0` берём, только если влезает; иначе `q4_0`. `q8_0` точнее для JSON
в аргументах инструментов, но на 8 ГБ с 9B-моделью места на него нет.

### Reasoning-модель в агенте: бюджет обрезает ответ

`llm.prediction.reasoning.budgetTokens` - поле вида `{checked, value}`. Если `checked: true`,
модель **останавливается**, исчерпав бюджет, и пользователь получает обрывок ответа.

Реальный случай: бюджет 1024, в логе `n_gen = 941` - генерация кончилась у самой границы.
Со стороны UI это выглядит как «модель отвечает ерундой в три слова», и виноватой кажется
сама модель. Дефолт у разных моделей разный: у одной `{checked: false, value: 8192}`
(без лимита), у другой может стоять `{checked: true, value: 1024}`.

**Перед использованием reasoning-модели в агенте это поле надо проверить.** Нужны длинные
ответы - лимит снять, а не задирать значение.

### Размер контекста под агента

Системный промпт агента с описаниями инструментов - **не константа**. Замерено на WorkBuddy:
за одну сессию он вырос с 37955 до 41025 токенов по мере подключения инструментов и скиллов.

Отсюда практика: контекст, равный промпту агента плюс чуть-чуть, бесполезен. При 49152 и
промпте 41025 на разговор остаётся ~8k, и агент уходит в аварийную компакцию после первого
же хода - а каждая компакция это ещё один полный вызов модели. Разумный ориентир для
агентской работы - **примерно вдвое больше промпта агента**.

### Кэш префикса

Ключевая вещь для агентской петли. Замер на живом сервере (промпт ~4900 токенов):

```
ход 1 (холодный)         5.14s
ход 2 (тот же префикс)   0.43s   -> ускорение 12x
ход 3 (тот же префикс)   0.43s
ход 4 (история выросла)  0.54s   -> префикс переиспользуется и при растущем диалоге
```

Статичная часть промпта агента префиллится **один раз**, дальше обрабатывается только дельта.

**Но кэш живёт в одном слоте и обнуляется любым посторонним запросом к той же модели.**
Проверено на практике: 19 крупных запросов в логе движка шли полностью холодными
(`prompt processing ... progress = 0.08`), потому что между ними шли короткие пробы от
`weds check`. Каждая такая проба стоит ~40 секунд холодного префилла на следующем ходу агента.

Отсюда правило: **не запускать `weds` параллельно с работой агента на той же модели.**
Проверять модель - до или после сессии, не во время.

Проверка `prefix_cache` строит промпт с уникальным nonce в начале: кэш в llama.cpp матчится
от первых токенов, и без nonce разные проверки попадали бы в кэш друг друга, а замеры врали.

### Per-model конфиги LM Studio

Путь:

```
<home>/apps/<app>/.internal/user-concrete-model-default-config/<publisher>/<model>/<file>.gguf.json
```

`<home>` берётся из `~/.lmstudio-home-pointer` - home можно перенести, и хардкод тут не работает.

Формат - плоский список `{key, value}`. Значение бывает трёх видов:

- число - `{"key": "llm.load.contextLength", "value": 32768}`
- boolean - `{"key": "llm.load.llama.flashAttention", "value": true}`
- поле с галочкой-включателем - `{"key": "...kCacheQuantizationType", "value": {"checked": true, "value": "q4_0"}}`

Проверенные ключи и их дефолты:

| Ключ | Тип | Дефолт |
|---|---|---|
| `llm.load.contextLength` | int | - |
| `llm.load.numParallelSessions` | int | **4** |
| `llm.load.llama.acceleration.offloadRatio` | 0..1 / `"max"` / `"off"` | авто |
| `llm.load.llama.flashAttention` | bool | **false** |
| `llm.load.llama.evalBatchSize` | int | **2048** |
| `llm.load.llama.physicalBatchSize` | int | 512 |
| `llm.load.llama.contextCheckpoints` | int | 32 |
| `llm.load.llama.cpuThreadPoolSize` | int | - |
| `llm.load.offloadKVCacheToGpu` | bool | **false** |
| `llm.load.llama.kCacheQuantizationType` | `{checked,value}` | F16 |
| `llm.load.llama.vCacheQuantizationType` | `{checked,value}` | F16 |

`--apply` всегда делает бэкап (`<файл>.weds-backup`). Откат: `weds restore --model <key>`.

### Чтение логов движка

Логи - самый честный источник данных, потому что UI врёт:

```
<home>/apps/<app>/server-logs/YYYY-MM/YYYY-MM-DD.N.log
```

Оттуда берутся:
- `request (N tokens) exceeds the available context size (M)` - настоящая причина ошибки
- `load_model: initializing, n_slots = N, n_ctx_slot = M` - что реально применилось
- `Estimated model usage ...` - вес модели и цена контекста

Важная деталь: `estimatedRemainingBytes` в этих записях - это **VRAM + системная RAM**,
а не VRAM. Именно поэтому LM Studio позволяет загрузить модель, которой нужно 12.9 ГБ,
на карту с 8 ГБ, и уронить отзывчивость всей системы.

## Ограничения

- **Тюнинг конфигов - только для LM Studio / Bionic.** У Ollama и llama.cpp per-model
  конфигов в таком виде нет; `check`, `bench`, `register` работают с ними нормально.
- **Определение VRAM.** Сначала `nvidia-smi`; если NVML заблокирован - реестр Windows
  (`HardwareInformation.qwMemorySize`). Если не сработало ни то, ни другое - бюджет задаётся
  вручную: `--vram-gib 8`. Это не ошибка, так и задумано: молча угадывать хуже, чем спросить.
  Значение из реестра - вся память карты, без учёта уже занятого рабочим столом.
- **Проекция памяти пессимистична.** Оценщик LM Studio завышает расход, поэтому вывод
  «не влезает» - это предупреждение. Решение принимается по `weds bench` на живой загрузке;
  бюджет можно задать напрямую через `--budget-gib`.
- **Размер промпта агента задаётся числом**, а не измеряется автоматически. Точное значение
  для конкретной обвязки видно в логе движка после первой ошибки - оттуда и берётся.
  Учти: промпт растёт вместе с числом инструментов, за сессию он менялся с 37955 до 40018 токенов.
- **Физические ядра CPU** определяются через CIM, при неудаче - эвристикой «логические / 2».
  Для llama.cpp нужно именно физическое число.
- Гибридные архитектуры (attention + SSM) поддерживаются через эмпирическую кривую памяти,
  а не через аналитический расчёт.

## Что проверено на живом железе

i3-12100 (4P/8T), 16 ГБ DDR4, RTX 2060 Super 8 ГБ, Windows, Bionic 1.0.9 / LM Studio 0.4.x,
модель Ornith-1.5-9B Q4_K_M:

| Параметр | Было | Стало |
|---|---|---|
| `offloadRatio` | 0.8125 (26/32 слоёв) | `max` |
| генерация | 17.8 tok/s | **41–46 tok/s** |
| `flashAttention` | false | true |
| `evalBatchSize` | 2048 | 256 |
| `numParallelSessions` | 4 | 1 |
| KV-кеш | `q4_0` при 55k | `q4_0` при 49k |
| контекст | 55 274 | 49 152 |
| `context_fit` | падал с ошибкой | проходит |

Префилл: 869 tok/s (холодный, 38k токенов), генерация 40–46 tok/s.

Отдельный прогон под работу агентом в чате (WorkBuddy, промпт агента 41025 токенов):

| Параметр | Было | Стало |
|---|---|---|
| контекст | 49 152 | **98 304** |
| бюджет разговора | ~8k токенов | **~57k токенов** |
| `reasoning.budgetTokens` | `{checked: true, 1024}` | `{checked: false, 8192}` |
| `offloadKVCacheToGpu` | не задан | **true** |
| генерация | 34.1 tok/s | **46.9 tok/s** |
| VRAM процесса | 5667 MiB | 6303 MiB |
| свободно VRAM | 2122 MiB | 1524 MiB |

Цена контекста по факту: **12.8–13.5 КиБ/токен**, а не 47 КиБ как в базовой оценке.
Причина - гибридная архитектура: полный attention только в 8 слоях из 32.

Замер VRAM делался счётчиками производительности Windows, без NVML:
`Get-Counter '\GPU Adapter Memory(*)\Dedicated Usage'` и `'\GPU Process Memory(*)\Dedicated Usage'`.
Это точнее любой аналитики и работает там, где `nvidia-smi` падает.

## modellab: тестер-оптимизатор локальных моделей

Отдельное приложение в `modellab/`, для другой задачи: не «готова ли модель к агентской
работе», а **что вообще влезает на это железо и в каком режиме**. Спидометры tok/s,
полосы памяти против порога, подбор максимального контекста по прямой расхода VRAM,
сравнение конфигураций перемежающимися прогонами и выгрузка готового лаунчера в `.cmd`.

```
python -m modellab.gui            # http://127.0.0.1:8090
```

Главное, что он умеет и чего не видно из обычных замеров: ловить копию весов в системной
памяти (`--load-mode none`: рабочий набор 6072 → 945 МБ, decode 9.87 → 17.90 tok/s) и рост
памяти от контрольных точек контекста (902 → 3055 МБ за пять замеров, decode 17.29 → 7.2).
Отказывает до старта с объяснением, если свободной памяти не хватает, и не трогает чужие
процессы. Подробности, измерения и список ловушек - в [`modellab/README.md`](modellab/README.md).
