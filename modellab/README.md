# modellab - тестер-оптимизатор локальных моделей

Приложение для одной задачи: **выжать из слабого железа максимум, не уронив машину.**
На i3-12100 / 16 ГБ / RTX 2060 Super 8 ГБ вопрос стоит не «какая скорость», а «что вообще
влезает», поэтому память и скорость измеряются вместе, а не по отдельности.

Без зависимостей - только стандартная библиотека Python 3.9+.

```
python -m modellab.gui              # http://127.0.0.1:8090
python -m modellab.gui --open       # и сразу открыть браузер
python -m modellab.gui --models D:\gguf
```

---

## Зачем отдельное приложение

Работа с тяжёлой моделью на 16 ГБ упирается в две вещи, которые не видны из графиков
производительности:

1. **Копия весов в системной памяти.** Движок по умолчанию держит весь GGUF в рабочем
   наборе, даже когда все слои уже на карте. На этой машине: mmap → рабочий набор 6072 МБ,
   свободно 1919 МБ, decode 9.87 tok/s; `--load-mode none` → рабочий набор 945 МБ,
   свободно 6931 МБ, decode 17.90 tok/s. Разница в разы, и именно она превращала машину
   в неотвечающую.
2. **Рост памяти на длинном прогоне.** Контрольные точки контекста дублируют рекуррентное
   состояние: за серию из пяти замеров рабочий набор вырос 902 → 3055 МБ
   (23 точки по 149.626 МиБ), а decode упал с 17.29 до 7.2 tok/s.

Поэтому приложение измеряет скорость и память одним прогоном и **никогда** не запускает
два тяжёлых задания одновременно - две копии модели на одной карте дают цифры, которые
нельзя сравнивать.

## Что внутри

| Файл | Назначение |
|---|---|
| `probe.py` | Датчики: память системы и процесса, CPU, GPU, разбор лога движка, preflight, список потребителей памяти |
| `watchdog.py` | Сторож на время прогона: два критерия (физическая память и commit), `MeasurementAborted` при пробитии пола |
| `llamasrv.py` | Запуск `llama-server`, конфиг, вывод `--load-mode` из числа слоёв, поиск бинарника |
| `measure.py` | Замер через SSE: TTFT, устойчивая скорость, дрожание, префилл |
| `lab.py` | Состояние, один рабочий поток, кеши, `atexit`-остановка сервера |
| `search.py` | Подбор конфига, профили, сравнение A/B, выгрузка `.cmd` |
| `gui.py` | `http.server` + проверка заголовка `Host`; один статический файл вместо Electron |
| `static/index.html` | Страница целиком: спидометры, полосы памяти, графики, таблицы |

**Почему не Electron/Tauri.** Приложение измеряет свободную память, а любой браузерный
рантайм держит в памяти сотни мегабайт и попадает в тот же бюджет, который мы измеряем.
`http.server` плюс один HTML-файл стоят около 15 МБ.

**Почему UI слушает только 127.0.0.1 и проверяет `Host`.** Иначе страница на любом сайте
могла бы обратиться к API по localhost (DNS rebinding) и запустить сервер на чужой
конфигурации.

## Подбор конфигурации

Перебор тут плох: одна загрузка модели стоит ~50 с холодной, а сетка по контексту
(4k/8k/16k/32k/64k) - это пять минут ради одной цифры. Вместо перебора берутся **две**
загрузки на разных ctx, и расход VRAM от контекста описывается прямой:

```
ctx_max = (свободно - веса - резерв - intercept) / наклон
```

Измерено на Ternary-Bonsai-2-27B (KV q4_0, flash-attn on):

| ctx | контекст, МБ | вычисления, МБ | всего сверх весов |
|---|---|---|---|
| 4096 | 221 | 126 | 347 |
| 32768 | 725 | 240 | 965 |
| 49152 | 1013 | 320 | 1333 |
| 65536 | 1301 | 410 | 1711 |

Прямая по первым двум точкам: `260 + 0.02155·ctx` МБ, наклон **22.1 МБ на 1024 токена**.
Третья и четвёртая точки в подгонке не участвовали и проверяют её: предсказание
6714 против фактических 6729 (ошибка 0.2 %) и 7067 против 7107 (0.6 %). Ошибка меньше
резерва 256 МБ, поэтому резерв её и покрывает.

**Резерв 256 МБ, а не 1024 МБ, как в собственном целевом показателе движка.** Движок
печатает `cannot meet free memory target of 1024 MiB`, но загружается и работает: его
проекция переоценивает расход примерно на 100 МБ (7097 МБ проекции против 7000 МБ
свободных дали рабочие 17.9 tok/s). Большой резерв просто съедал бы контекст зря.

### Профиль - это не только число, но и обстоятельства

Профиль хранит, сколько VRAM было свободно и какой запас оставался. Свободная VRAM на этой
машине плавает на сотни мегабайт от одного рабочего стола (движок на загрузке видел
7000 МБ, `nvidia-smi` через две минуты - 7488 МБ), поэтому «профиль говорит 49152» само по
себе не значит, что сегодня 49152 влезет. При переиспользовании сравнивается **разность**
(насколько сейчас теснее, чем было), и если карта стала теснее больше чем на записанный
запас - профиль не применяется, нужен новый замер.

### Что получилось на этой машине

```
ctx 49152   веса 5395 + контекст 1013 + вычисления 320 = 6729 МБ при 7000 МБ свободных
            запас 286 МБ по прямой (фактически движок оставил 271 МБ)
            14.6–17.3 tok/s, префилл 109–167 tok/s, host_ratio 0.31
```

## Сравнение A/B: почему не «замерить A, замерить B и сравнить»

На этой машине одна и та же конфигурация в соседних прогонах дала **8.12 и 15.38 tok/s** -
разброс в 1.9 раза. Он берётся не из модели, а из окружения: рабочий стол, браузер,
обновление кеша ОС, тепловой режим карты. На таком фоне однократное сравнение измеряет шум.

Поэтому прогоны **перемежаются**: A, B, A, B, … Каждая пара видит примерно одно состояние
машины, и сравнивать надо разности внутри пары, а не средние по конфигурациям. Знак разности
должен быть одинаковым во всех парах - тогда эффект реален; если знак скачет, различие
меньше шума, и это тоже результат, а не неудача.

Пример реального вывода (KV q4_0 против q8_0, ctx 32768, 3 пары):

```
разности: [-0.98, -0.02, +0.26] tok/s → знак меняется, эффект НЕ доказан
но: KV q4_0 буферы VRAM 6371 МБ, контекст 725 МБ
    KV q8_0 буферы VRAM 6883 МБ, контекст 1237 МБ
```

Скорость в пределах шума, а память отличается ровно и воспроизводимо: **q8_0 стоит
+512 МБ VRAM и не даёт ничего.** Это и есть ответ, ради которого сравнение делалось.

Флаги, которые не удалось подтвердить: `--cache-ram 0` и `--ctx-checkpoints 0` рост памяти
останавливают (23 точки → 0, рабочий набор стабилен на 935 МБ), но влияние на скорость
не воспроизводится - знак разности скачет. Это настройка под задачу (долгая сессия против
максимальной скорости), а не «правильное значение».

## Ловушки, закодированные в приложении

Всё ниже стоило времени и записано в коде комментариями, чтобы не повторилось.

- **`-lv 4` обязателен для учёта памяти.** Только на этой подробности движок печатает
  бюджет VRAM и строки `buffer size`. На дефолтном `-lv 3` в логе полностью загруженной
  модели этих строк нет вообще.
- **`--load-mode` нужен и `llama-bench`.** Без него бенчмарк втянет 5.67 ГБ в системную
  память - тот самый сценарий зависания.
- **Агрегат `eval time` бесполезен**, а контрольные точки подменяют опорную копию: свежий
  сервер стартует с точки, сделанной на предыдущем, никогда не остановленном запуске.
- **Префилл берётся только с первого прогона.** С кешем префикса повтор читает промпт
  из кеша: измеренные 1352 tok/s против честных 167–190. Признак - `cache_n` в таймингах.
  Каждому повтору даётся свой seed, чтобы кеш не мог превратить замер префилла в попадание.
- **Время загрузки определяется диском, а не картой:** 46–53 с холодной, 3.5–4.5 с тёплой.
- **`nvidia-smi` может отдавать 255** (`Failed to initialize NVML`) - тогда единственный
  источник VRAM это лог движка, и приложение говорит об этом вслух, а не показывает ноль.
- **Пути на Windows приходят в двух написаниях.** Git Bash переписывает `E:\…` в `E:/…`,
  из-за чего одна и та же модель выглядела как две разные и список моделей молча
  переключался на первую подходящую. Нормализация на обеих сторонах - в `ServerConfig`
  и в сравнении в UI.
- **`.cmd` для лаунчера - CRLF и только ASCII.** `cmd.exe` неправильно разбирает LF-only
  bat-файлы, а не-ASCII байты в консоли cp866/cp1251 ломают разбор. Заголовок пишется
  по-английски именно поэтому.
- **Кавычки вокруг подстановки команды недопустимы.** Строка `"  -m "%LAB_MODEL%"` разбирается
  как имя команды, и лаунчер не запускается ни при каких настройках.
- **В команде должен быть исполняемый файл.** Файл, где `LAB_BIN` задан и нигде не
  использован, а команда начинается с `-m`, выглядит правдоподобно и не работает вообще.
- **`taskkill /F /IM` бесполезен** там, где есть супервизор: он поднимет сервер заново
  через 5 с. Гасить надо по pid с `/T`.
- **Сравнивать размеры логов для определения нового запуска нельзя** - логи старта на
  `-lv 3` байт-идентичны. Надо смотреть mtime.

## Защита от «уронил машину»

- `preflight` перед каждым стартом: пол свободной физической памяти (1500 МБ по умолчанию),
  потребность конфига (600 МБ для `none`/`dio`, иначе 1.1×размер + 600), commit, и список
  процессов-потребителей. Отказ - с причиной и именами, а не молчаливое падение.
- `MemoryWatchdog` во время прогона, с двумя критериями: пик физической памяти приходится
  на загрузку (2486 МБ однажды пробили пол 2500 МБ на здоровой загрузке), а исчерпание
  commit - это и есть настоящее «машина замерла».
- Одно тяжёлое задание за раз, `taskkill /T` по дереву процессов, `atexit`-остановка.
- **Чужие процессы не убиваются.** Однажды бенчмарк был прерван полом из-за постороннего
  `llama-server` (pid 6780, 5875 МБ) - он не был тронут, а приложение научили отказывать
  заранее с объяснением.

## Тесты

```
python tests/smoke_probe.py      # датчики: 25 проверок на живом железе и реальном логе
python tests/smoke_core.py       # статика: конфиг, сторож, порт, двойник, профили
python tests/smoke_core.py --live   # плюс живой прогон на модели 0.8B
python tests/smoke_export.py     # выгрузка .cmd и профили: 66 проверок
python tests/accept_api.py       # приёмка через API самого UI
```

`smoke_export.py` разбирает сгенерированный `.cmd` так, как его прочитал бы `cmd.exe`
(снимает `rem`, склеивает продолжения по каретке, подставляет `%переменные%`, разбирает
кавычки), и сверяет полученную командную строку с `cfg.to_argv()`. Именно эта проверка
поймала лаунчер без исполняемого файла, без `-c` и с кавычками вокруг команды - файл
создавался, был непустой и выглядел правдоподобно.

## Границы применимости

- **`host_ratio` для маленьких моделей больше единицы** (у 0.8B измерено 1.65): в рабочий
  набор входит контекст CUDA, который для модели в 500 МБ сопоставим с самими весами.
  Сравнивать `host_ratio` между моделями разного размера нельзя, только между режимами
  одной модели.
- **Потолок по контексту считается от свободной VRAM, а не от полной.** Часть карты занимает
  рабочий стол: 8191 МБ всего против 7000 МБ свободных в момент старта движка.
- **`nvidia-smi` и движок считают свободное по-разному**, расхождение достигает ~500 МБ.
  Поэтому проверка профиля сравнивает разность, а не абсолют.
- **Потолок по контексту - это не максимум скорости.** Наибольший влезающий контекст
  оставляет меньше запаса; 49152 выбран как компромисс, а не как оптимум по tok/s.
- **Дефолт `ctx` в форме - 65536**, как в рабочем `start-bonsai.cmd`. Подбор на текущем
  состоянии карты даёт 49152: при 7000 МБ свободных 65536 не влезает (нужно ~7107 МБ),
  и это как раз причина, по которой рабочему лаунчеру нужен супервизор.
