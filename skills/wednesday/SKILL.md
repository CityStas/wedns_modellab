# Wednesday — проверка локальных моделей перед работой агентом

Инструмент лежит в `F:\Pets\Cursor\Wednesday`. Запуск без установки:

```bash
python F:/Pets/Cursor/Wednesday/weds.py <команда>
```

Путь машинозависимый: на другой машине его нужно поправить в этом файле и в MCP-конфиге.
Если MCP-сервер Wednesday подключён, путь знать не надо — вызывать инструменты напрямую.

Все команды поддерживают `--json`. Общие флаги (`--json`, `--model`, `--server-url`,
`--agent-tokens`) работают и до, и после подкоманды.

## Порядок действий при любой жалобе на локальную модель

1. `doctor` — одна команда, показывает всё сразу.
2. Если нужно глубже — `logs`, затем `check`.
3. Лечение — `tune --apply` (с бэкапом), откат — `restore`.

```bash
python weds.py doctor
python weds.py doctor --fast          # без тяжёлых проверок
python weds.py check --model <id>
python weds.py logs --limit 5
python weds.py tune --model <key> --apply
python weds.py restore --model <key>
```

Модель можно указывать подстрокой: `--model ornith` разрешается в точный id сам.

**VRAM определяется автоматически** — сначала `nvidia-smi`, при заблокированном NVML —
из реестра Windows (`HardwareInformation.qwMemorySize`). `--vram-gib` нужен, только если
не сработало ни то, ни другое. Проверить: `python weds.py tune --model <key>` покажет
блок «Железо» с полем `source`.

## Главное правило: UI врёт, лог не врёт

Сообщение в интерфейсе вида

```
Custom model custom-local:ornith-1.5-9b-crack error. Please switch model or retry.
```

**не содержит причины**. Настоящая ошибка — в логе движка:

```
Engine protocol predict request returned 400:
request (37955 tokens) exceeds the available context size (32768 tokens)
```

Поэтому при жалобе на «Custom model error» **первым делом** смотреть `weds logs`,
а не гадать. `weds logs` сам вытащит ошибки переполнения и посчитает нужный контекст.

## Что почти всегда оказывается причиной

### 1. Промпт агента не влезает в контекст

Системный промпт агента с описаниями инструментов — **≈38 000–40 000 токенов** (WorkBuddy;
за сессию менялся с 37955 до 40018 по мере роста числа инструментов). Контекст меньше
этого = падение каждого запроса.

Ставить контекст **не меньше 49152**, даже если модель «помещается» в 32768.
Для простого чата хватит и 32768, для агента — нет.

Точное число для конкретной обвязки берётся из лога движка после первой ошибки —
оттуда же его читает `weds logs`.

### 2. Переполнение VRAM маскируется под «модель тормозит»

Признак: **префилл быстрый, генерация обвалилась в 10–20 раз.**

Префилл читает память батчами последовательно и остаётся быстрым (~900 tok/s), а генерация
на каждый токен перечитывает KV-кеш вразнобой и упирается в PCIe. Это не баг модели,
перезагрузка не поможет — только снижение KV-кванта или контекста.

LM Studio **не блокирует** переполнение VRAM: `estimatedRemainingBytes` в его логах —
это VRAM **плюс системная RAM**, поэтому он грузит конфиг на 12.9 ГБ в карту на 8 ГБ
и вешает всю систему.

### 3. Часть слоёв осталась на CPU

`offloadRatio 0.8125` = 26 из 32 слоёв. Оставшиеся 6 упираются в память DDR4
(~47 ГБ/с против 448 ГБ/с у видеокарты) и определяют скорость. Полный оффлоад
(`offloadRatio: "max"`) даёт **2.3× на генерации** — проверено: 17.8 → 41 tok/s.

Если веса влезают в VRAM — грузить `--gpu max`, даже ценой контекста.

### 4. `flashAttention` по умолчанию выключен

Это неочевидно и всегда стоит включить: `llm.load.llama.flashAttention: true`.
При квантованном KV-кеше он обязателен.

### 5. `numParallelSessions` по умолчанию 4

Для одного пользователя — только `1`. Дефолт вчетверо делит пул контекста.

### 6. Две копии модели в памяти

Повторные загрузки с разными параметрами создают второй инстанс (`model:2`).
Два 9B на карте 8 ГБ = ~10.5 ГБ весов. Всегда `lms unload --all` перед сменой параметров.

## Диагностический признак, который стоит запомнить

> **Префилл быстрый, генерация обвалилась → не хватает VRAM.**

Обратное тоже верно: **и генерация, и префилл медленные** → слои на CPU, нужен полный оффлоад.

## Подбор параметров

`tune` измеряет кривую памяти движка двумя вызовами `lms load --estimate-only`
(модель при этом не загружается, система не нагружается) и подбирает контекст под бюджет VRAM.

```bash
python weds.py tune --model <key>            # только показать
python weds.py tune --model <key> --apply    # записать (с бэкапом)
python weds.py tune --model <key> --budget-gib 7 --apply   # бюджет вручную
python weds.py tune --model <key> --kv-in-ram --apply      # экономить VRAM
```

Логика выбора KV: сначала `q8_0` (точнее для JSON в tool-call'ах), откат на `q4_0`,
если по бюджету не влезает. На 8 ГБ с 9B-моделью почти всегда `q4_0`.

`offloadKVCacheToGpu` ставится в `true` по умолчанию: замерено 34 → 47 tok/s. Если после
загрузки генерация провалилась — `--kv-in-ram`.

**Оценщик LM Studio завышает расход — проекция это предупреждение, а не приговор.**
Проверено: проекция говорила «не влезает» при 49152 на 8-гиговой карте, а модель на этом
контексте выдавала 52 tok/s. Поэтому если `tune` пишет «ВНИМАНИЕ: не влезает», а `bench`
после загрузки показывает нормальные tok/s — верить `bench`, а бюджет задать через
`--budget-gib`. Не откатывать контекст только из-за проекции.

**Реальную VRAM мерить счётчиками, а не оценкой:**
`Get-Counter '\GPU Adapter Memory(*)\Dedicated Usage'` и `'\GPU Process Memory(*)\Dedicated Usage'`.
Работает без NVML. Так выясняется настоящая цена контекста: у гибридных архитектур это
**12–14 КиБ/токен**, а не 47 как в базовой оценке.

**Ручной расчёт KV по метаданным GGUF не использовать** — для гибридных архитектур
(attention + SSM, например `qwen35`) он врёт в разы. Только эмпирика.

## Регистрация модели в агенте

```bash
python weds.py register --model <id> --target workbuddy
python weds.py register --model <id> --target workbuddy --dry-run
python weds.py register --model <id> --target env      # переменные окружения
```

**Никогда не добавлять `availableModels`** в `models.json` — этот ключ схлопывает дропдаун
до перечисленных id и вырезает все облачные модели. `register` его не пишет.

## Осторожность

- `check` без `--fast` и `bench` **тяжёлые**: холодный префилл 38k токенов занимает
  до минуты и грузит GPU на полную. Если пользователь жаловался на лаги — сначала
  `--fast`, тяжёлые проверки отдельным прогоном и по одной.
- `tune --apply` пишет в конфиг LM Studio. Всегда есть бэкап (`<файл>.weds-backup`),
  откат — `weds restore --model <key>`. Сообщать пользователю путь бэкапа.
  Бэкап создаётся один раз и повторными `--apply` не перетирается — в нём исходное состояние.
- Не гонять серию тяжёлых тестов подряд: это само по себе вешает систему на слабой карте.
- **Не запускать проверки, пока пользователь работает с той же моделью в чате.** KV-кеш
  живёт в одном слоте, и любой посторонний запрос его обнуляет: следующий ход агента
  получит полный холодный префилл ~40 с вместо ~0.5 с. Проверять модель до или после сессии.
- **Reasoning-бюджет проверять до жалоб на «глупые ответы».** Поле
  `llm.prediction.reasoning.budgetTokens` с `checked: true` обрывает генерацию на границе
  бюджета: пользователь видит обрывок ответа и винит модель. Симптом в логе — `n_gen`
  вплотную к значению бюджета.
